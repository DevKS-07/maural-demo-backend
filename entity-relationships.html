Maural Knowledge Hub — Entity Relationships & Business Context

A conceptual breakdown of every entity in the system, what it represents in the business domain, and how entities relate to one another.

1. The Business Model at a Glance

Maural Solutions LLC is a consulting firm that serves multiple organisations simultaneously. The Knowledge Management System (KMS) is built as a multi-tenant platform — meaning a single deployment of the application serves every organisation, but each organisation's data is logically isolated from every other organisation's data. Think of it like an apartment building: the building is one structure (one application), but each apartment (each organisation/tenant) has its own locked door, its own contents, and its own residents. The landlord (Maural Solutions / Super Admin) has a master key and can manage the building, but tenants only see their own apartment.

Within this model, there are two distinct sides of the platform:

  • The administrative side — operated by Maural Solutions staff (Super Admins and Admins) who onboard organisations, manage the platform, oversee all tenants, and access cross-organisation analytics.
  • The organisation side — operated by the organisation's own employees (Org Executives and Org Staff) who manage their own documents, view their own dashboards, and interact with the AI chatbot scoped to their organisation's knowledge base.

2. Entity Definitions

Organisation (Tenant) Core Entity

An Organisation represents a distinct organisation that Maural Solutions serves. In multi-tenant terminology, each Organisation is a tenant. Examples might be "Acme Corp," "Greenfield Industries," or "Lakewood Medical Group." Each Organisation record stores the organisation's profile information — its name (org_name), industry, founding date, key contacts, location, and organizational chart reference.

Critically, each Organisation is assigned its own storage bucket (a UUID-identified container in Supabase Storage). This is the tenant isolation boundary for documents: all files belonging to an organisation are stored in that organisation's bucket, and the system enforces that users from one organisation can never access another organisation's bucket. The Organisation entity is the anchor point of the entire data model — Users belong to an Organisation, Files belong to an Organisation, and KPI data (financial, leads, labor) is scoped to an Organisation.

The gpt_types field indicates which AI/chatbot capabilities have been enabled for that organisation, allowing Maural to customize the AI experience per organisation. Additionally, boolean flags (hubspot_connected, quickbooks_connected, monday_connected, clickup_connected) track which external integrations have been connected for this organisation.

Has many: Users, Files, FinanceKpis, LeadsKpis, LaborKpis, document_embeddings

Has one: VTO (strategic plan — vision, values, goals)

Has one (per service): HubspotToken, QuickbooksToken, MondayToken, ClickUpToken

Business meaning: "This is one of the companies we serve."

User Core Entity

A User is any individual person who logs into the platform. Every User has a name, email, phone, demographic fields, and a job_title field, along with a clerk_id that links them to their identity in the external authentication provider (Clerk). The User record in the database is the internal profile — it stores application-specific data (role assignment, organisation membership, activity tracking), while Clerk handles the authentication concerns (password hashing, session tokens, MFA).

Each User optionally belongs to an Organisation. This "optionally" is important: Maural Solutions' own staff (Super Admins and Admins) are Users who are not assigned to any specific Organisation — they exist above the tenant boundary and can see across all organisations. In contrast, organisation-side users (Org Executives and Org Staff) are always associated with exactly one Organisation, and the system uses this org_id foreign key to enforce tenant isolation throughout every API query.

Each User is assigned exactly one Role, which determines what they can see and do within the platform. Users can also upload Files, and the system tracks who uploaded each document.

Belongs to: Organisation (optional — null for Maural staff), Role

Has many: Files (uploaded by this user)

Linked to: Clerk (external auth provider) via clerk_id

Business meaning: "This is a person who uses the platform."

Role Auth & Access

A Role defines a level of access within the platform. The system implements a strict four-tier role hierarchy:

Role Level Scope Who This Is
Super Admin 4 (highest) Platform-wide Maural Solutions system administrator. Full control over all organisations, users, and system configuration.
Admin 3 Platform-wide Maural Solutions consultant or manager. Can manage organisations and users but may not have system-level configuration access.
Org Executive 2 Own organisation only A senior person within the organisation (e.g., CEO, VP). Can manage their org's users, documents, view dashboards, and access analytics — but only for their own organisation.
Org Staff 1 (lowest) Own organisation only A regular employee within the organisation. Can view and upload documents, use the chatbot, and access their organisation's knowledge base — with more limited management capabilities.

The RBAC middleware enforces this hierarchy: any endpoint can declare a minimum required role, and the system compares the requesting user's role level against the minimum. A level-2 user can access any endpoint requiring level 1 or 2, but not level 3 or 4. This is a hierarchical (or "tiered") RBAC model, as opposed to a flat role model where each role is independent.

Has many: Users, RolePermissions

Business meaning: "This defines what a class of users is allowed to do."

Permission & RolePermission Auth & Access

A Permission represents a specific, granular action that can be performed in the system (e.g., "create_document", "delete_user", "view_dashboard"). The RolePermission entity is a junction table that creates a many-to-many relationship between Roles and Permissions — meaning each Role can have multiple Permissions, and each Permission can be assigned to multiple Roles.

This two-layer approach (hierarchical role levels plus granular permissions) gives the system flexibility. The role hierarchy handles the broad "who outranks whom" logic, while the permission assignments handle fine-grained "can this role specifically do X?" checks. For example, both Admin and Org Executive might be at different hierarchy levels, but both could share a "view_financial_reports" permission if the business requires it.

RolePermission bridges: Role ↔ Permission (many-to-many)

Business meaning: "These are the specific capabilities assigned to each role."

File (Document) Knowledge Base

A File represents a document that has been uploaded into the knowledge base. This is the central asset of the KMS — the whole purpose of the platform is to store, organize, retrieve, and derive insights from these files. Files can be PDFs, spreadsheets (XLSX), Word documents (DOCX), images, or other business documents.

Each File record stores metadata: the file name, file size, and file_source (where it came from — e.g., direct upload, a HubSpot integration, a QuickBooks export). The actual file content is stored in Supabase Storage within the owning Organisation's dedicated storage bucket — the database only holds the metadata and the reference, not the binary content itself.

Files are categorized (linked to a Category) for organizational purposes, and the system tracks who uploaded them (linked to a User). When a file is uploaded, the ingestion pipeline processes it: extracting text content, generating vector embeddings via Ollama, and storing those embeddings in the document_embeddings table so the AI chatbot can later retrieve relevant documents during a conversation.

Belongs to: Organisation (tenant ownership), Category (organizational), User (uploader)

Processed into: document_embeddings (for AI retrieval)

Stored in: Supabase Storage (Organisation's dedicated bucket)

Business meaning: "This is a piece of knowledge that the organization has stored in the system."

Category Knowledge Base

A Category is a classification label used to organize Files within the knowledge base. Categories might include labels like "Legal," "Financial," "HR," "Marketing," "Operations," or "Contracts." They provide a human-readable organizational structure so users can browse and filter documents by type rather than having to search through a flat list.

Categories are shared across all organisations — they are not tenant-scoped. This means "Financial" as a category means the same thing for every organisation. The tenant isolation is enforced at the File level (each file belongs to a specific organisation), not at the category level.

Has many: Files

Business meaning: "This is a way to classify and organize documents by type."

Document Embeddings AI / Chatbot

The document_embeddings table is the foundation of the AI chatbot's knowledge. When a File is ingested, the system extracts its text content, splits it into meaningful chunks, and passes each chunk through an embedding model (Ollama) to generate a high-dimensional vector representation. These vectors capture the semantic meaning of the text — not just keywords, but the concepts and relationships within the content.

Each record stores the original text content (so it can be shown to the user), a metadata JSON field (containing the source file reference, page numbers, etc.), and the embedding vector itself. The vector column uses PostgreSQL's pgvector extension, which enables similarity search — when a user asks the chatbot a question, the question is also embedded into a vector, and the system finds the document chunks whose vectors are closest to the question vector. This is the Retrieval-Augmented Generation (RAG) pattern.

Each embedding row has a real org_id UUID column (foreign key → Organisation) that enables tenant-scoped vector search at the database level. The match_documents RPC function accepts a filter_org_ids parameter and uses WHERE org_id = ANY(filter_org_ids) to restrict results to the caller's organisation — or returns all results when filter_org_ids is NULL (admin mode). A B-tree index on org_id ensures fast tenant-scoped queries. The foreign key uses ON DELETE CASCADE, so deleting an organisation automatically removes all its embeddings.

Belongs to: Organisation (via org_id FK, ON DELETE CASCADE)

Derived from: Files (via the ingestion pipeline)

Used by: RAG service → Chat controller → AI chatbot responses

Business meaning: "This is the AI-searchable representation of our document knowledge base, scoped per organisation for tenant isolation."

FinanceKpi / LeadsKpi / LaborKpi Analytics & Dashboards

The three KPI models store periodic business intelligence snapshots pulled from external systems. They are the data behind the organisation dashboards and represent the "analytics and insight generation" pillar of the platform.

FinanceKpi

Financial performance data sourced primarily from QuickBooks. Each record is a time-bounded snapshot (defined by periodStart and periodEnd) of an organisation's financial health: revenue, gross profit, net income, EBITDA, cash position, accounts receivable, monthly burn rate, cash runway, working capital, days sales outstanding (DSO), and valuation metrics (Rule of 40, enterprise value). It also stores budget-vs-actuals variance percentages. This gives Org Executives and Maural consultants a financial dashboard without needing to log into QuickBooks directly.

LeadsKpi

Sales pipeline and business health data sourced primarily from HubSpot. Tracks the sales funnel (leads → calls → proposals → deals won → conversion rate), revenue composition (recurring vs. one-time), pipeline coverage, client concentration risk (how dependent revenue is on the top 5 clients/customers), founder dependency in sales, deal velocity, forecast accuracy, and retention rate. This paints a picture of an organisation's go-to-market health and growth trajectory.

LaborKpi

Workforce and utilization data sourced from project management tools — Monday.com or ClickUp. Tracks direct labor hours, headcount (billable vs. non-billable FTEs), billable utilization rate, labor cost per hour, revenue per billable FTE, and founder dependency on service delivery. For consulting firms, utilization and labor efficiency are often the most critical operational metrics.

All three KPI models follow the same structural pattern: they are scoped to an Organisation, bounded by a time period, and include cache metadata (lastFetchedAt, isStale, fetchSource) to support background data refresh without blocking the dashboard UI. The unique constraint on [org_id, periodStart, periodEnd] ensures there is exactly one snapshot per organisation per period — refreshing the same period overwrites the existing record rather than creating duplicates.

Belongs to: Organisation

Sourced from: QuickBooks (finance), HubSpot (leads), Monday.com/ClickUp (labor)

Business meaning: "These are the business performance metrics we track for each organisation over time."

VTO (Vision/Traction Organizer) Knowledge Base

The VTO entity stores an organisation's strategic planning document — the Vision/Traction Organizer. Each Organisation has at most one VTO (enforced by a unique constraint on org_id). The VTO captures the organisation's core values, mission and vision statements, 10-year targets, marketing strategy (target market, proven process, differentiators, guarantee), and a 3-year picture (revenue targets, profit targets, measurables).

VTO data is not just stored — it is actively used by the AI chatbot. When a user asks a business strategy question, the Business Data Service fetches the organisation's VTO from the database and injects it into the chatbot's system prompt alongside KPI data and document embeddings. This means the chatbot can answer questions like "What are our core values?" or "What's our 3-year revenue target?" using authoritative strategic data rather than relying on general knowledge.

Belongs to: Organisation (one-to-one via unique org_id, ON DELETE CASCADE)

Used by: Business Data Service → Chat controller → AI chatbot responses

Business meaning: "This is the organisation's strategic plan — its vision, values, and goals."

HubspotToken / QuickbooksToken / MondayToken / ClickUpToken Integrations

The four Token models store OAuth2 credentials for each external integration. When an organisation connects their HubSpot, QuickBooks, Monday.com, or ClickUp account to the KMS, the OAuth2 handshake produces tokens which are stored in these tables. The access token is used for API calls to the external service; the refresh token (where available) is used to obtain a new access token when the current one expires. Note that ClickUp tokens are long-lived and do not include a refresh token or expiry.

Each token record is keyed by org_id, meaning the integration is tied to the organisation that authorized it. The tokens belong to the organisation as a whole, not to any individual user — this ensures that the integration persists regardless of which user initiated the OAuth flow. The system uses these stored tokens to periodically fetch KPI data and populate the FinanceKpi, LeadsKpi, and LaborKpi tables.

Belongs to: Organisation (via org_id)

Enables: Data fetching for KPI models

Business meaning: "These are the saved credentials that let us pull data from external tools on behalf of an organisation."

4. Key Relationship Patterns

Tenant Isolation (The Most Important Pattern)

The org_id foreign key is the single most important relationship in the entire data model. It appears on Users, Files, FinanceKpis, LeadsKpis, LaborKpis, and document_embeddings. Every API query that returns tenant-scoped data filters by org_id to ensure that a user from Organisation A can never see Organisation B's documents, users, or KPI data. This isolation is enforced at multiple layers: the application code (API controllers filter by org_id), the database (row-level security policies, foreign keys with ON DELETE CASCADE), and the storage layer (each organisation has its own Supabase Storage bucket). The AI chatbot enforces this boundary at the database level — the document_embeddings table has a real org_id UUID column with a B-tree index, and the match_documents RPC function uses WHERE org_id = ANY(filter_org_ids) to scope vector search results to the requesting user's organisation. Admin users can pass NULL to search across all organisations.

Authentication vs. Authorization (Two Separate Systems)

Authentication (proving who you are) is handled entirely by Clerk, an external identity provider. Clerk manages user registration, login, password hashing, session tokens, and multi-factor authentication. When a user logs in, Clerk issues a JWT (JSON Web Token) that the frontend sends with every API request.

Authorization (determining what you can do) is handled by the KMS itself. The requireAuth middleware verifies the Clerk JWT, then the requireRole middleware checks the user's role from the JWT's public metadata against the endpoint's minimum required role level. The Role and Permission entities in the database define the authorization model, while Clerk defines the authentication model. The clerk_id on the User entity is the bridge between the two systems.

The Document-to-Intelligence Pipeline

There is a directional flow from raw document to AI-ready knowledge:

File upload → Supabase Storage → Ingestion pipeline → Text extraction (PDF/DOCX/XLSX/OCR) → Embedding generation (Ollama) → document_embeddings table → RAG retrieval → Chatbot response

This pipeline transforms a static document (a PDF sitting in storage) into searchable, AI-queryable knowledge. The File entity represents the document as an organizational asset; the document_embeddings entity represents the same content as semantic vectors that the AI can reason over. They are two representations of the same underlying knowledge, connected through the ingestion pipeline.

In addition to document embeddings, the chatbot also receives live business data context on every request. The Business Data Service fetches the latest KPI snapshots (Financial, Leads, Labor) and VTO data from the database — in parallel with intent detection and document retrieval — and injects them into the LLM system prompt. This means the chatbot can answer questions grounded in three data sources simultaneously: document embeddings (RAG), structured KPI metrics, and strategic VTO data — all scoped to the requesting user's organisation.

External Data Flow (Integrations → KPIs → Dashboards)

The integration tokens enable a second data pipeline:

Organisation authorizes OAuth → Token stored → System fetches data from external API → Data transformed into KPI snapshots → Stored in FinanceKpi/LeadsKpi/LaborKpi → Rendered on organisation dashboard

This pipeline transforms raw data from multiple external tools (QuickBooks for finances, HubSpot for sales/leads, Monday.com or ClickUp for labor) into a unified dashboard experience. The organisation doesn't need to log into four different tools and mentally synthesize the data — the KMS pulls it all together into a coherent business intelligence view with computed metrics like EBITDA margin, cash runway, utilization rates, and conversion rates.
